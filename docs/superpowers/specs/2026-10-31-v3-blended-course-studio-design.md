# Course Curriculum Creator v3 — Blended Course Studio

**Date:** 2026-10-31
**Status:** Draft for review (builder check done; owner answers incorporated)
**Supersedes direction of:** `2026-03-15-course-curriculum-enhancements-design.md` (implemented in v1.1/v2.0)
**Version target:** v3.0.0 (breaking)

---

## 1. Intent

Today the plugin turns a topic into a well-designed **1–2 day facilitated workshop expressed as markdown**: objectives, rubrics, outline, lesson plans, handouts. The pedagogy is strong; the outputs are a textbook.

v3 turns it into a **blended course studio**. The facilitated session stays the pedagogical core, but the plugin now also produces what learners and facilitators actually *use*:

- a **learner hub** (interactive site) that carries learners before, during, and after live sessions — explainers, interactive diagrams, self-check quizzes, tracked progress, and an AI tutor;
- **media**: explainer diagrams, data visualizations, illustrations, infographics/cheat sheets, audio recaps, and (later) explainer video;
- **designed deliverables**: real slide decks, print-ready branded workbooks/PDFs;
- **publishing**: the hub is one portable site that deploys to any host (Claude Artifacts, ChatGPT Sites, Cloudflare, Vercel, Netlify, GitHub Pages, or a zip), plus LMS packages (SCORM/cmi5);
- support for **flexible course shapes**: workshop, multi-session cohort, and self-paced.

**Why:** the owner wants to go "beyond a simple textbook" — courses whose materials teach on their own between and around live sessions, with visuals that do real explanatory work.

## 2. Goals, non-goals, anti-goals

### Goals
1. Every course has a single machine-readable source of truth (`course.yaml` + markdown + media registry) from which all outputs are rendered.
2. Media is **planned pedagogically** (each asset serves a named objective and a named instructional function), **approved by the user** before money is spent, then generated and reviewed.
3. The plugin uses whatever media MCPs/connectors are available at run time and **degrades gracefully** to code-rendered or placeholder output when they aren't.
4. One hub source publishes to four targets, using each target's native capabilities for tutor and tracking.
5. Brand-consistent output: an optional user brand configuration underlies a per-course style guide that every renderer and every image prompt obeys.
6. Course shapes beyond 1–2 day workshops.
7. Fix the structural debt found in review (duplication, prose-implemented logic, no tests).

### Non-goals (v3)
- Being an LMS, video editor, or design tool. The plugin produces and packages; it doesn't host learners itself (except via the targets' own hosting).
- Selling/commerce, payments, enrollment management.
- Authoring for non-course content (marketing sites, social posts).
- Real-time multi-user hub features beyond what a target natively provides.

### Anti-goals (would be a failure even if it works)
| Anti-goal | Design response |
|---|---|
| **Inaccurate visuals** (garbled text, wrong technical content) in materials | Raster images are generated **text-free**; all labels are a separate SVG/HTML layer. Every asset passes a vision self-review checklist and explicit user approval before it is referenced by any material. Diagrams are generated from structured specs derived from lesson content. |
| **Runaway cost** | Per-course budget in `course.yaml`; cost estimate on every plan item; a ledger of actual spend; generation hard-stops at the cap. Nothing paid runs without plan approval. |
| **Bloat / slowness** | Plugin family: users who only want markdown install only the core. Media and publishing never run implicitly; the core workflow's speed and UX must not regress. |
| **Vendor lock-in** | Markdown + `course.yaml` + files on disk are the source of truth. Every asset keeps its source (prompt, spec, diagram JSON) so it can be regenerated by another provider. Every target adapter is optional and replaceable. A course must remain fully usable with zero MCPs connected. |

## 4. Review of the current plugin (v2.0.0)

Inventory: 25 workflow skills (`workflow/<stage>/<name>/SKILL.md`), 4 knowledge skills, 2 agents (`curriculum-architect`, `quality-reviewer`), ~11k lines of markdown, no code, no tests.

**Strengths to keep:** backward-design ordering; Bloom's/Krathwohl depth; UDL, accessibility, cultural adaptation, content-curation references; TNA → learner profile → objectives → rubrics → outline → lesson plans chain; staleness concept; templates; series design; Kirkpatrick evaluation; spaced practice.

**Findings (each becomes a refactor item in §8):**

| # | Finding | Impact |
|---|---|---|
| R1 | Settings block duplicated in 17 skills; staleness check re-implemented as prose (`md5sum … \| cut -c1-8`) in 10 skills | Drift, inconsistent behavior, token waste; logic is non-deterministic because the model executes prose |
| R2 | No course manifest. Course state is scattered across frontmatter; skills find inputs by filename convention; no stable IDs for objectives/modules | Nothing downstream (media, hub, LMS) can reference "LO-3" or "Module 2" reliably |
| R3 | 1–2 day duration hard-coded (~78 references across skills/agents) | Blocks cohort and self-paced shapes |
| R4 | `curriculum-architect` reads raw `SKILL.md` files (because workflow skills are `disable-model-invocation`), runs the whole course in one context, pinned to `model: sonnet` | Fragile, not resumable, context-heavy; model pin ages badly |
| R5 | Output is markdown only. `--type slides` = an outline. Export = concatenate + "try pandoc" | The "textbook" ceiling the owner wants to break |
| R6 | No visual/media planning anywhere; UDL says "≥2 representation modes per module" and accessibility spec requires alt text/captions, but nothing produces or enforces them | Guidance without enforcement |
| R7 | No tests or evals (`claude plugin eval` now exists) | Regressions invisible |
| R8 | AskUserQuestion used in 11/23 workflow skills; interaction style inconsistent | Uneven UX |
| R9 | Accessibility reference targets WCAG 2.1 AA | WCAG 2.2 is current |
| R10 | `marketplace.json` is single-plugin with `source: "./"` | Must restructure for a plugin family |

## 5. Research findings that shape the design

As of 2026-10-31. Sources in §14. Items marked *(verify)* rest on secondary sources and must be re-checked when the relevant phase starts.

**Claude Code plugin platform**
- `userConfig` supports `sensitive: true` (stored in OS secure storage); `${user_config.KEY}` is substituted in MCP server `env`/`args` and in non-sensitive skill content. Sensitive values never appear in skill content.
- `dependencies` lets one plugin require another (bare name resolves in the same marketplace).
- `${CLAUDE_PLUGIN_DATA}` persists across updates — the place for installed `node_modules`, caches, browsers.
- A top-level **`bin/` prevents install on claude.ai and Cowork** → the toolkit goes inside a skill folder (see §7.1a), never a top-level `bin/`.
- Component paths must stay inside the plugin root → plugins cannot share a sibling folder at runtime; shared code must be bundled into each plugin.
- `experimental.evals` + `claude plugin eval` provide a test harness.
- Skills cannot enumerate MCP tools programmatically; **Claude sees its tool list** — detection is an instruction to the model plus a recorded result.

**Claude Artifacts** (from Claude Code's Artifact tool)
- Multi-file HTML artifacts publish from Claude Code; private by default, shareable by the owner.
- Runtime capabilities include shared database, "ask Claude", viewer identity, file handling → natural home for **tutor + tracking + cohort dashboard**.
- Requires the publishing user to be on claude.ai; viewers' access model is set at share time.

**ChatGPT** *(verify)*
- Canvas share links are **legacy**; canvas reportedly left current models in May 2026. Not a viable target.
- **ChatGPT Sites** (public beta since July 2026): websites/light apps built in ChatGPT or Codex, hosted on Cloudflare Workers with optional D1 (SQLite) and R2; access can be private, workspace, selected users, or public; Sign in with ChatGPT for public sites. Paid plans only (not Free/Go); not in EEA/CH/UK at launch.
- **No publish API.** Deployment is by asking Codex "Deploy this project with Sites"; the link is stored in `.openai/hosting.json`.
- Apps SDK (MCP-based apps in ChatGPT) exists but requires directory review — out of scope for v3.
- Custom GPTs remain the simplest ChatGPT-side tutor.

**Images**
- OpenAI `gpt-image-2` is current; token-priced (reported ~$30/M output image tokens) *(verify)*. Only community MCP servers wrap it — none official.
- Gamma connector exposes `generate_image` (available in the owner's environment).
- **Codex CLI generates images natively** via its bundled `$imagegen` skill / built-in `image_gen` tool (gpt-image-2 default since April 2026), callable non-interactively as `codex exec '$imagegen …'`. In its default mode it uses the logged-in **ChatGPT session — no API key, billed against the ChatGPT plan** rather than per token; it falls back to `OPENAI_API_KEY` otherwise. Transparent backgrounds route to gpt-image-1.5 *(verify flags/feature gate)*. The owner has Codex CLI installed (`codex-cli 0.166.0`) and the Codex Claude Code plugin.

**Diagrams**
- Excalidraw has an **official remote MCP** (`https://mcp.excalidraw.com/mcp`): element-format reference, draw, export to shareable excalidraw.com link *(verify tool names)*. Owner has the claude.ai Excalidraw connector (requires auth).
- Mermaid renders locally (mermaid-cli) and via the Mermaid Chart connector.

**Video & audio**
- Code video: **HyperFrames** (HTML scenes → MP4 via headless Chrome + FFmpeg, agent-oriented, ships skills not MCP) and **Remotion** (React). Manim for math-style animation.
- Generative video: Higgsfield has community MCPs only (aggregates Kling, Veo, Sora, etc.).
- OpenAI TTS (`gpt-4o-mini-tts`) ≈ 1.5–2¢/minute *(verify)*.

**LMS**
- No good static generator for SCORM/cmi5 exists. Writing `imsmanifest.xml` / `cmi5.xml` directly and using ADL's `@xapi/cmi5` runtime is the cleanest path; `lxpack` is a reference implementation.

## 6. Approaches considered

| Approach | Summary | Trade-off |
|---|---|---|
| **A. Plugin family on a shared data contract (chosen)** | `course.yaml` + media registry as the contract; Node toolkit bundled into each plugin; three plugins: core, studio, publish | Most up-front structure. Directly answers bloat (install only core), lock-in (contract on disk), cost/accuracy (enforced in code, not prose) |
| B. Single v3 plugin | Same contract and toolkit, one plugin | Simpler release; every user carries media machinery and its config prompts |
| C. Skills-only extension | New prose skills that write HTML, call MCPs, publish | Fastest; cannot enforce budget caps, review gates, SCORM correctness, or reproducibility — fails the anti-goals |

**Chosen: A**, with Node/TypeScript toolkit.

## 7. Architecture

### 7.1 Repository and plugin layout

The repo becomes a monorepo marketplace:

```
course-curriculum-creator/                  (repo root = marketplace)
├── .claude-plugin/marketplace.json         three plugin entries
├── packages/
│   └── course-kit/                         TypeScript source of the shared toolkit
│       ├── src/ (manifest, hash, registry, ledger, render, package, providers)
│       └── test/
├── plugins/
│   ├── course-curriculum-creator/          CORE (existing content moves here)
│   │   ├── .claude-plugin/plugin.json
│   │   ├── workflow/… skills/… agents/…
│   │   ├── skills/course-kit/scripts/course-kit.mjs   bundled build of course-kit (inside a skill folder so it loads on every surface, see §7.1a)
│   │   └── evals/
│   ├── course-studio/                      MEDIA + DESIGNED DELIVERABLES
│   │   ├── .claude-plugin/plugin.json      dependencies: ["course-curriculum-creator"]
│   │   ├── .mcp.json                       thin fallback media server (see 7.6)
│   │   ├── skills/… scripts/… evals/
│   └── course-publish/                     HUB + TARGET ADAPTERS
│       ├── .claude-plugin/plugin.json      dependencies: ["course-curriculum-creator"]
│       ├── skills/… scripts/… hub-runtime/ evals/
├── docs/
└── README.md
```

- `packages/course-kit` is built (esbuild) into a single `.mjs` per plugin and **committed** into each plugin's `skills/course-kit/scripts/` (plugins install from git; containment rules forbid sharing a sibling folder). A CI check fails if bundles are stale.
- Heavy optional dependencies (Playwright/Chromium for PDF and PNG rendering, mermaid-cli, pptxgenjs, HyperFrames) are installed **lazily** into `${CLAUDE_PLUGIN_DATA}` by a `setup` skill in studio/publish the first time they are needed, with the user's consent.
- Runtime requirement: **Node ≥ 20 for all three plugins** (owner confirmed). There are no prose fallbacks for logic that `course-kit` implements.
- All three plugins share the `course-curriculum-creator` marketplace; namespaces become `/course-curriculum-creator:…`, `/course-studio:…`, `/course-publish:…`.

### 7.1a Surface support (Claude Code, Cowork, claude.ai chat)

Per Anthropic's platform-support matrix, each surface loads a different subset of a plugin:

| Capability | Claude Code | Cowork | claude.ai chat |
|---|---|---|---|
| Skills | ✓ | ✓ | ✓ |
| Agents, hooks | ✓ | ✓ | ignored |
| Local (stdio) MCP, e.g. `course-media` | ✓ | only when the session runs on the user's computer | ignored |
| MCP using `${user_config.*}` | ✓ (prompts) | ignored unless every referenced option has a default; Cowork never prompts | ignored if in URL |
| Remote connectors (Excalidraw, Gamma, Mermaid Chart) | ✓ | ✓ | ✓ |
| Top-level `bin/` | ✓ | refuses install | refuses install |
| Persistent course folder | ✓ | ✓ | ✗ |
| Codex CLI | ✓ if installed | *(verify)* | ✗ |

**Design consequences (my call: "Cowork full, chat light"):**
- **Claude Code** is the full-power surface.
- **Cowork** runs the whole studio and publish workflow. To make that work:
  - **The scripts live inside skill folders.** Each plugin ships `skills/course-kit/scripts/course-kit.mjs`, with no top-level `bin/` or plugin-level `scripts/`. Skills reference the bundled file relative to the `course-kit` skill directory, so the same instruction works on every surface.
  - **The `course-media` server loads in Cowork.** Every `userConfig` field it references has a default (`""`), so the server isn't dropped. It falls back to `OPENAI_API_KEY` from the environment, or to a key file in `${CLAUDE_PLUGIN_DATA}`. When no key is found, it reports "not configured".
  - **Media falls back to connectors.** When the local server or Codex is unavailable, provider routing (§7.6) uses the remote connectors.
- **claude.ai chat** handles the core curriculum skills, connector-based diagrams, and quick previews. Course files come back as downloadable outputs. Chat doesn't support the full media pipeline, hub builds, or deploys, and skills say so and point to Cowork or Claude Code.
- Lazy installs of heavy dependencies (Playwright, mermaid-cli) may be blocked by sandbox network rules in Cowork *(verify)*. Every renderer therefore needs a lighter fallback: Mermaid via the connector, or an SVG authored directly. HTML→PDF falls back to print-ready HTML that the user prints.

### 7.2 The course data contract

#### `course.yaml` (new, at course root)

```yaml
schema: course/v3
id: proptech-fundamentals            # slug, stable
title: PropTech Fundamentals
version: 0.3.0
status: draft
created: 2026-10-31
shape: workshop                      # workshop | cohort | self-paced
delivery: in-person                  # in-person | virtual | hybrid | async
audience: { level: professional, summary: "Commercial real estate analysts" }
timeBudget:                          # replaces hard-coded 1-2 day logic
  live:                              # omitted for self-paced
    sessions:
      - { id: S1, label: "Day 1", minutes: 420 }
      - { id: S2, label: "Day 2", minutes: 420 }
  async:
    preWorkMinutes: 60
    betweenSessionMinutes: 0
    postWorkMinutes: 90
objectives:                          # stable IDs; text lives in learning-objectives.md
  - { id: LO-1, bloom: apply, domain: cognitive }
modules:
  - { id: M1, title: "…", session: S1, objectives: [LO-1, LO-2], minutes: 90 }
brand: ~/.config/course-brand/acme.brand.yaml   # optional, overrides userConfig
style: 05-media/style/style-guide.md
media:
  budgetUsd: 25.00
  maxPlanImages: 40                  # cap for plan-billed generation (e.g. Codex $imagegen)
  approvalRequired: true
outputs:
  hub: { hosts: [zip, chatgpt-sites], tutorUrl: "https://chatgpt.com/g/…", tracking: hosted }   # tracking: local|hosted|lms
  lms: { formats: [scorm12] }
targets: {}                          # filled by publish adapters: artifact URL, sites project id, etc.
```

- `course-kit manifest validate` checks schema + cross-references (every module's objectives exist; minutes fit the time budget per shape rules).
- Stable IDs (`LO-n`, `M n`, `S n`, `A-…`) are written into markdown headings as anchors (`## Module 1: Title {#M1}`) so renderers can resolve them. Existing markdown remains human-first.

#### v3 course directory

```
<course>/
├── course.yaml
├── 01-planning/  02-design/  03-assessment/  04-materials/     (as today)
├── 05-media/
│   ├── style/            style-guide.md, tokens.json, prompt-anchors.md
│   ├── media-plan.yaml   planned assets awaiting/after approval
│   ├── registry.json     every asset: id, type, function, objective(s), module, provider,
│   │                     source (prompt/spec/json path), files, alt, longDescription,
│   │                     caption, status, costUsd, sha256, reviewedBy, createdAt
│   ├── src/              regenerable sources: prompts, mermaid, excalidraw json, vega-lite specs, narration scripts
│   └── out/              rendered files: svg, png, webp, mp3, vtt, mp4
├── 06-hub/               hub content model (hub.json) + per-page overrides
├── dist/                 build outputs (gitignored): site/ (+ functions/), lms/, slides/, pdf/
└── .course/              cost-ledger.jsonl, providers.json, logs (gitignored except ledger)
```

#### Staleness, done in code
`course-kit stale <output>` reads the output's frontmatter `sourceHashes`, recomputes, and prints a structured result. `course-kit hash --write <output>` updates frontmatter. All skills call these instead of embedding md5 prose. The registry also tracks asset → source hashes, so editing a lesson flags dependent media and hub pages as stale.

### 7.3 Course shapes

| Shape | Live component | Async component | Key pedagogical adjustments |
|---|---|---|---|
| **workshop** | 1–2 sessions (today's default) | pre-work, spaced post-work | Unchanged behavior; time budget derived from sessions |
| **cohort** | N sessions over weeks (e.g., 6 × 90 min) | between-session assignments, discussion prompts, spaced practice | Each session opens with retrieval of previous; assignments are transfer tasks; facilitator guide per session |
| **self-paced** | none | entire course | More worked examples and faded scaffolding; every module ends with interactive practice + feedback; explicit time-on-task estimates; hub is the primary delivery surface; rubric-based assessments become auto-checkable items or self-assessment with model answers |

All 78 duration references are replaced by reading `timeBudget` + `shape` through the shared conventions (see 8.1). `create-course` asks for shape first.

### 7.4 Media pipeline (course-studio)

```
lesson plans + style guide
        │
   plan-media ──► media-plan.yaml (status: proposed, est. cost)
        │
   user approves / edits (AskUserQuestion per module or bulk)
        │
   generate-media ──► provider routing ──► 05-media/src + out, registry (status: generated), ledger
        │
   review-media ──► vision checklist ──► user approve/reject/regenerate ──► registry (status: approved)
        │
   embed ──► markdown materials, slides, workbook, hub reference approved assets only
```

**Planning rules** (`plan-media`):
- Each planned asset declares `function` from a fixed taxonomy: `concept-map`, `process-flow`, `comparison`, `hierarchy`, `cycle`, `timeline`, `data-viz`, `worked-example`, `scenario-illustration`, `analogy-illustration`, `infographic`, `job-aid`, `interactive-explainer`, `audio-recap`, `video-explainer`.
- Each asset links ≥1 objective and the lesson segment it supports. No objective, no asset (anti-decoration).
- Mayer's multimedia principles are encoded as plan-review checks: coherence (no decorative images), signaling, redundancy (no narrated text read verbatim), spatial/temporal contiguity, segmenting.
- UDL check: every module has ≥2 representation modes (closes R6).
- Text-heavy or precise visuals (process flows, labeled structures) route to **diagram tools**, never raster generation.
- Estimate cost per item from `pricing.json` (bundled, dated, user-overridable); show module and course totals vs budget.

**Accuracy rules** (`generate-media`, `review-media`):
- Raster image prompts are composed from: style-guide prompt anchors + scene description + mandatory "no text, letters, numbers, logos, or watermarks". Any needed labels go in an SVG overlay rendered with the course fonts.
- Vision self-review checklist per asset: stray/garbled text; factual/technical correctness against the lesson segment; representation & cultural fit (cultural-adaptation reference); style conformance; contrast/legibility; anatomical or physical errors. Failures auto-regenerate once (counted against budget), then go to the user.
- Nothing reaches `approved` without explicit user approval (bulk approve allowed). Unapproved assets render as labeled placeholders in any output.
- Every asset gets alt text; complex diagrams get a long description; audio/video get transcripts and WebVTT captions.

### 7.5 Brand and style

- **Brand configuration (user-specified, optional):** a `*.brand.yaml` file referenced by core `userConfig.brand_config` (type `file`) and overridable per course in `course.yaml`. Schema: name, logo(s) (light/dark, SVG preferred), color palette (primary/secondary/neutral/semantic), fonts (heading/body/mono with web-font source or local files), voice & tone notes, imagery style (illustration vs photo, do/don't lists), accessibility constraints. A `setup-brand` skill creates/validates one interactively (can extract from an existing site or PDF the user points at).
- **Per-course style guide:** `generate-style-guide` derives `tokens.json` (colors, type scale, spacing, radii — WCAG 2.2 AA contrast-validated) and `prompt-anchors.md` (a fixed illustration style description, palette words, composition rules, and a reference image set once the first images are approved). With no brand config, it designs a theme from the course topic and audience.
- Every renderer (hub, slides, workbook, infographics, diagrams' theme, video scenes) consumes `tokens.json`; every image prompt includes the anchors.

### 7.6 Provider detection and routing

**Detection.** Before generating, `generate-media` instructs Claude to inspect its available tools and record matches into `.course/providers.json` via `course-kit providers record` (capability → tool name, detected-at). Known patterns are listed in a bundled `providers.yaml` (e.g., Excalidraw connector `*Excalidraw*`, Mermaid Chart, Gamma `generate_image`, any `*image*`/`generate_image` tool, Higgsfield, ElevenLabs). Users can pin or exclude providers in `course.yaml`.

**Codex as a provider.** If `codex` is on PATH and logged in (`course-kit providers probe codex` runs `codex login status` or equivalent), image generation can be delegated with `codex exec '$imagegen <composed prompt> — save to <abs path>'` in a sandbox restricted to `05-media/out/`. The composed prompt (style anchors + no-text rule) is identical to other providers, and the prompt is saved to `05-media/src/` as usual. Codex runs are recorded in the ledger with `costUsd: 0` and `quotaUnits: 1` (plan-billed), and a per-course `media.maxPlanImages` cap applies so plan quota can't be burned silently.

**Fallback MCP server (my proposal).** `course-studio/.mcp.json` declares a small stdio server `course-media` (built from course-kit) exposing `generate_image`, `edit_image`, `synthesize_speech`, `estimate_cost`. It reads `openai_api_key` from a **sensitive** studio `userConfig` field via `env`. Unconfigured, it reports "not configured" rather than failing. This is one provider among others, so it doesn't contradict detect-and-degrade; it guarantees the owner's OpenAI key is usable without a community server.

**Routing table (first available wins; user can override per asset):**

| Asset function | Preferred | Fallback 1 | Fallback 2 |
|---|---|---|---|
| Hand-drawn concept/process diagram | Excalidraw MCP (draw + export) | Excalidraw JSON authored locally → rendered SVG via `@excalidraw/utils` | Mermaid → SVG |
| Precise flow/sequence/hierarchy/timeline | Mermaid (local mermaid-cli) | Mermaid Chart connector | Hand-authored SVG |
| Data visualization | Vega-Lite spec rendered locally | — | Table + description |
| Illustration / scenario / analogy | **Codex `$imagegen`** (plan-billed, no key) | Detected image MCP or `course-media.generate_image` (gpt-image-2, API key) → Gamma `generate_image` | Placeholder + saved prompt |
| Infographic / job aid / cheat sheet | HTML+SVG template rendered to PNG/PDF via Playwright (+ approved illustrations) | — | Markdown one-pager |
| Audio recap | `course-media.synthesize_speech` (OpenAI TTS) or detected TTS MCP | — | Script only |
| Video (Phase 6) | HyperFrames/Remotion local render; generative via detected Higgsfield/Sora MCP | Narrated slideshow (images + TTS + captions) | Storyboard + script only |

All sources (prompt, spec, JSON, script) are saved in `05-media/src/` regardless of provider (anti-lock-in).

**Cost control.** `course-kit ledger` appends every paid call (provider, model, units, estimated vs actual USD, plan-quota units, asset id). `generate-media` refuses an item that would exceed `media.budgetUsd`; the user can raise the budget explicitly. Studio `userConfig.default_media_budget_usd` sets the default.

### 7.7 Designed deliverables (course-studio)

| Skill | Output | How |
|---|---|---|
| `generate-slides` | `dist/slides/deck.html` (keyboard-navigable HTML deck) + `deck.pptx` with speaker notes | From outline + lesson plans + approved media; pptx via `pptxgenjs` using tokens; optional Gamma generation when the connector is present (user choice) |
| `generate-workbook` | `dist/pdf/workbook.pdf`, `facilitator-guide.pdf` | Markdown → HTML print templates (Paged.js-style CSS) → PDF via Playwright; tagged PDF, bookmarks, alt text |
| `generate-infographic` | per-module one-pagers + course cheat sheet (PNG + PDF) | HTML/SVG templates + tokens |
| `generate-audio` | per-module recap MP3 + transcript + VTT, scripts for spaced-practice prompts | Narration script written for the ear (not read-aloud text), TTS via routing |
| `generate-video` (Phase 6) | MP4 + VTT + transcript | See routing table; storyboard approval step before render |

The existing core `generate-artifacts --type slides` is retired in favor of `course-studio:generate-slides` (core keeps markdown handouts/guides/assessments).

### 7.8 Learner hub (course-publish)

**Content model.** `build-hub` compiles `course.yaml` + markdown + approved registry into `06-hub/hub.json`: pages (Home, Before, per-Session/Module, After, Resources), blocks, assets, quiz items, interactives. Users may hand-edit per-page overrides; rebuilds preserve them.

**Practice content is authored, not compiled (my call).** Today's courses don't contain quiz items, flip cards, sort/match sets or scenarios. A separate `generate-practice-items` skill writes them to `06-hub/practice.yaml`. Each item carries the objective ID and Bloom level it targets, an answer key, feedback for each distractor, and a source citation to the lesson segment. The skill follows the same **plan → approve** gate as media, and items stay unapproved until the user signs off. `build-hub` is then deterministic: it only renders approved items and assets. The core spaced-practice question bank is reused as seed material.

**Structure by shape.** Workshop: Before (pre-work units, readiness check) → Sessions (module explainers, in-room interactives, slide links) → After (spaced-practice schedule, recaps, job aids). Cohort: timeline of sessions with between-session assignments. Self-paced: linear modules with gating by completion.

**Interactive catalog (v3):** step-through explainer, labeled-diagram hotspots, reveal/flip cards, sort/order, match, scenario branching, parameter slider for simple models, and quiz items (single/multi choice, ordering, matching, short answer with model answer). Each interactive type is a vanilla web component in `hub-runtime/` (no framework, no build step at the user's side), themed by `tokens.json`, keyboard- and screen-reader-accessible.

**Runtime abstraction.** Hub pages talk only to `CourseRuntime`:

```ts
interface CourseRuntime {
  learner(): Promise<{ id: string; name?: string } | null>;
  recordAttempt(itemId: string, response: unknown, score: number): Promise<void>;
  setProgress(pageId: string, state: 'started' | 'completed'): Promise<void>;
  getProgress(): Promise<Record<string, ProgressState>>;
  tutorLink(): string | null;                       // Custom GPT (or other) URL
}
```

There are three implementations, chosen at build time: **`local`** (localStorage, the default), **`lms`** (SCORM 1.2/2004 or cmi5), and **`hosted`** (calls the hub's own `/api/progress` function when the host supports functions). The runtime is deliberately independent of the host, so no host-specific runtime gets built.

### 7.9 Publishing: one portable site, interchangeable hosts (course-publish)

**Owner's principle:** Claude Artifacts, ChatGPT Sites, Vercel, Cloudflare, Netlify and the rest are all just places that host a website, and **it shouldn't matter which one the user deploys to**. The design follows from that:

- `build-hub` always produces **one portable site** in `dist/site/`. It's multi-page static HTML/CSS/JS with no framework, and it works from `file://` and on any static host.
- It optionally adds **`dist/site/functions/`**, a progress-store function written once against the **Workers/WinterCG fetch API**: `POST /api/progress` and `GET /api/progress`, plus an instructor `GET /api/report`, with SQLite/D1 storage. ChatGPT Sites runs on Cloudflare Workers with D1, so the same function serves Sites and Cloudflare without changes. Other hosts get a thin shim, or run the site with the `local` runtime.
- **Deploy adapters are thin and interchangeable.** Each one takes `dist/site/` and puts it on a host. They contain no content logic and no runtime differences beyond whether functions are available.

| Host adapter | How it deploys | Functions/tracking | Notes |
|---|---|---|---|
| `zip` (always) | `dist/<course>-site.zip` | none (local) | Hand to any host or IT department |
| `claude-artifact` | Artifact tool, multi-file publish | none (local); optional instructor-only extras below | Good for instructor previews and stakeholder review. External learners may not be able to open it |
| `chatgpt-sites` | With user confirmation, `codex exec "Deploy this project with Sites"` in `dist/site/`, which records `.openai/hosting.json`; falls back to `DEPLOY.md` | ✓ (Workers + D1) | Paid ChatGPT plans, region limits *(verify)*; no public API |
| `cloudflare` | `wrangler pages deploy` (or Workers static assets) | ✓ (same function, D1) | User's Cloudflare account |
| `vercel` / `netlify` | Their CLI deploy | via shim *(builder: shim, or static-only in v3)* | |
| `github-pages` | push to a `gh-pages` branch | none (local) | |

- **LMS packaging is a packager, not a host:** `package-lms` wraps the same `dist/site/` with the `lms` runtime into `dist/lms/<course>-scorm12.zip`, `-scorm2004.zip` and `-cmi5.zip`. There's one SCO per module (cohort/self-paced) or per session, and the mastery score comes from `course.yaml`.
- **Where tracking lives (the owner's choice for external learners):** in the client LMS (SCORM/cmi5), or on a host that runs functions (ChatGPT Sites or Cloudflare via `/api/progress`). A plain static site tracks only locally, on the learner's own device.
- **Learner identity on hosted sites:** the default is a learner-chosen name plus a per-browser ID, with an optional cohort access code. Sites can use Sign in with ChatGPT where it's enabled. Nothing more advanced is in v3.
- **Optional Claude Artifact extras** apply only when the audience has claude.ai access, such as an internal team, or the instructor themself. The extras are an instructor **cohort dashboard** that reads `/api/report` or LMS exports, and a Claude tutor. They're never needed for learner delivery.

**Tutor for external learners (owner's choice): Custom GPT.** `generate-tutor-pack` writes the GPT instructions: Socratic, scoped to the course objectives, refuses to complete graded work, and cites module pages. It also writes the knowledge files exported from the course, conversation starters, and a step-by-step `CUSTOM-GPT-SETUP.md`. There's no public API for creating GPTs, so the user creates the GPT once and pastes its URL into `course.yaml.outputs.hub.tutorUrl` *(verify at phase start whether creation can be automated)*. Every hub page then shows an "Ask the course tutor" link. Learners need a ChatGPT account, and a free one is enough. The same pack also exports as a Claude Project for internal audiences.

`publish` records each host's URL/ID in `course.yaml.targets`, and re-deploys in place on later runs.

### 7.10 Companion design skills (recommended, not required)

Presentation quality (hub pages, slide decks, infographics, workbook layout) gets much better with established frontend-design skills. The plugin **recommends** them, **detects** them, and **uses** them when they're present, but never requires them. That avoids lock-in, and cross-marketplace hard dependencies would force-install them.

| Companion | Repo | Install (Claude Code) | Used for |
|---|---|---|---|
| **Impeccable** | `pbakaus/impeccable` | `/plugin marketplace add pbakaus/impeccable` then install from `/plugin` | Design direction and polish of hub/slides; **`/impeccable audit` and `critique` as a post-build design quality gate** (deterministic anti-pattern detectors) |
| **Taste** | `Leonxlnx/taste-skill` (`design-taste-frontend`, plus `minimalist-ui`, `industrial-brutalist-ui`, `high-end-visual-design`) | `npx skills add https://github.com/Leonxlnx/taste-skill --skill "design-taste-frontend"` | Avoiding templated look; picking design variance, motion, and density per course audience |
| **UI UX Pro Max** | `nextlevelbuilder/ui-ux-pro-max-skill` | `/plugin marketplace add nextlevelbuilder/ui-ux-pro-max-skill` | Palettes, font pairings, chart and component guidance; seeds `generate-style-guide` when no brand config exists |
| Anthropic `frontend-design` / `web-artifacts-builder` | Anthropic skills | built in or via Anthropic marketplace | Baseline fallback |

**Behavior:**
- `course-studio:setup` and `course-publish:setup` check Claude's available-skills list for these names, then record the result in `.course/providers.json` under `designSkills`. For any that are missing, they print the install commands above and explain what each adds. They never install anything without the user saying yes.
- `generate-style-guide`, `build-hub`, `generate-slides`, `generate-infographic` and `generate-workbook` load the detected design skills before rendering. They pass them **the course's `tokens.json` and brand config as hard constraints**, along with the WCAG 2.2 AA and Mayer rules. Companion skills choose layout and composition, not brand colors or fonts.
- After a hub or deck build, if Impeccable is present, `review` runs its audit on the built HTML. Its findings are fixed or reported alongside the axe-core accessibility results.
- When none are installed, the built-in templates and token-driven CSS are used. The output is plainer but complete.
- The README gets a "Recommended companions" section with the table above.

## 8. Changes to the core plugin

1. **Shared conventions (closes R1).** New non-invocable knowledge skill `course-conventions` (settings resolution, manifest fields, ID conventions, staleness procedure, shape/time-budget rules, AskUserQuestion style). Workflow skills replace their duplicated blocks with a 2–3 line pointer and a `course-kit` call.
2. **Manifest + IDs (R2).** `create-course` writes `course.yaml`; objective/module generators assign and maintain IDs; `course-kit manifest sync` reconciles markdown ↔ manifest.
3. **Shapes (R3).** All duration logic reads `timeBudget`/`shape`. `create-course`, `generate-outline`, `generate-lesson-plans`, `generate-pre-work`, `generate-spaced-practice`, `adapt-for-virtual`, `design-series`, templates, and both agents updated.
4. **Agents (R4).** `curriculum-architect` becomes a resumable orchestrator: reads `course.yaml` for progress, runs each stage, writes progress back, and can stop/resume. Drop the `model: sonnet` pin (inherit). Builder decides whether stages run in forked contexts or subagents. `quality-reviewer` gains checks for manifest integrity, media alignment, accessibility of assets, and hub item coverage of objectives.
5. **`migrate-course` (new).** Converts a v2 course folder. It infers `course.yaml` from the positioning, objectives and outline frontmatter, assigns IDs, inserts anchors, and recomputes hashes. It runs dry by default and shows a diff summary. **The reference fixture is `reggiechan74/CRE-Courses/CRE-201`**, a real course that shows what migration must handle:
   - **The format doesn't fit "1–2 day".** `duration: "4-day (two weekends)"` should map to `shape: cohort` with 4 sessions, which comes from the outline's day headings. Free-text duration/format strings must be parsed, and the user confirms the result.
   - **Variant and extra files.** `course-outline-1day.md` alongside `course-outline.md` becomes a recorded *variant*. `teaching-notes.md` is a non-standard planning file, so it's preserved and registered as a source.
   - **Generated PDFs sit beside the markdown.** They're registered as derived outputs and never treated as sources.
   - **Custom-named materials and existing images** (`bmc.png`, `vpd.png`) are imported into the media registry with status `imported`. The user is asked for alt text and objective links during migration.
   - **Missing stages.** There are no lesson plans and a placeholder `04-materials/README.md`, so `course.yaml` records stage status as missing rather than failing.
   - **Non-standard objective numbering** ("Level 0", "Obj 1–10", integration pauses, affective objectives) maps to `LO-0…LO-10`, with `kind` values `orientation`, `integration` and `affective`.
   - **Extra frontmatter** (`courseVersion`, `revisionNote`, an `organization` value that differs per course) is preserved.
   - **External references** such as the series framework `../CRE_Series_Framework.md` are recorded as external sources.

   A copy of CRE-201 (or an anonymized snapshot of it) goes into `examples/fixtures/` for evals.
6. **Evals (R7).** `evals/` per plugin with cases for create-course, generate-objectives, manifest validation, migrate-course, plan-media (budget + objective-link rules), and hub build.
7. **Consistency (R8, R9).** Unified question style; accessibility reference updated to WCAG 2.2 AA.
8. **userConfig additions (core):** `brand_config` (file, optional), `default_shape` (`workshop|cohort|self-paced`). Existing keys kept.

## 11. Phasing

Each phase ships a usable increment.

**Release mapping (my call):** Phase 1 ships **core v2.1.0**, an additive release: `create-course` writes `course.yaml` and IDs alongside today's files, and v2 folders keep working. Alongside it ship **course-studio v0.1.0** and the monorepo restructure. Phase 2 ships **core v3.0.0** with the breaking changes and the full `migrate-course`. After that, each plugin versions independently.

| Phase | Scope | Exit criteria |
|---|---|---|
| **1 — Diagrams & images (first value)** | Monorepo restructure; `course-kit` (manifest minimal, registry, ledger, hash); `course.yaml` written by `create-course` and by `migrate-course` (minimal); course-studio with `setup-brand`, `generate-style-guide`, `plan-media`, `generate-media`, `review-media` for diagrams (Excalidraw/Mermaid), data viz, and illustrations (gpt-image-2 via `course-media` / detected MCP); embedding approved assets into existing markdown handouts, instructor guide, lesson plans | On a sample course: media plan generated and approved; ≥1 Excalidraw, Mermaid, Vega-Lite, and image asset produced, reviewed, embedded with alt text; budget cap enforced; works with zero MCPs (fallbacks) |

## 12. Testing strategy

- `packages/course-kit`: unit tests (vitest) for manifest schema, hashing, registry, ledger, budget enforcement, SCORM/cmi5 manifest generation, hub build.
- Plugin evals (`claude plugin eval`) per plugin for skill behavior.
- Golden sample courses in `examples/` (one per shape) used as fixtures; CI builds hub + LMS zips from them and diffs structure.
- Accessibility: automated axe-core run against built hub pages and slide HTML in CI.
- Manual test scripts for things CI can't reach: artifact publish, Sites deploy, SCORM Cloud upload, Excalidraw connector.
